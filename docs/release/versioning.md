# Keeva Automated Semantic Versioning

**Product:** Keeva  
**Developer:** Nishvanta Labs  
**Package:** `io.nishvanta.keeva`  

---

## 1. Overview

Keeva utilizes a fully automated Semantic Versioning (SemVer 2.0.0) release system coupled with strictly monotonic build numbers for mobile distribution.

Releases are evaluated and triggered automatically upon qualifying commits merging to the `main` branch. Maintainers and contributors do not manually edit version numbers or create git release tags for standard releases.

The canonical version source of truth is declared in `pubspec.yaml`:

```yaml
version: MAJOR.MINOR.PATCH+BUILD
```

- **`MAJOR.MINOR.PATCH`** $\rightarrow$ User-facing version string (`versionName` on Android, `CFBundleShortVersionString` on iOS).
- **`BUILD`** $\rightarrow$ Monotonically increasing positive integer (`versionCode` on Android, `CFBundleVersion` on iOS).

## 2. Release Types & Conventional Commits

The release engine evaluates commits on `main` since the latest git release tag to classify the required version increment:

### 2.1 PATCH Release (`fix:`)

- **Trigger:** Commits starting with `fix:` or `fix(...):`.
- **Semantics:** Backwards-compatible bug fixes, internal stability patches, error handling improvements.
- **Version Transition:**
  ```text
  1.0.0+1 → 1.0.1+2
  ```

### 2.2 MINOR Release (`feat:`)

- **Trigger:** Commits starting with `feat:` or `feat(...):`.
- **Semantics:** New user-facing features, functional capabilities, UI enhancements that remain backwards-compatible.
- **Version Transition:**
  ```text
  1.0.1+2 → 1.1.0+3
  ```

### 2.3 MAJOR Release (`feat!:` / `BREAKING CHANGE:`)

- **Trigger:** Commits with an exclamation mark after the type (e.g. `feat!:`, `fix!:`, `refactor!:`) or containing a footer `BREAKING CHANGE:` or `BREAKING-CHANGE:`.
- **Semantics:** Incompatible API changes, major architectural migrations, or foundational platform shifts.
- **Version Transition:**
  ```text
  1.1.0+3 → 2.0.0+4
  ```

### 2.4 Non-Releasing Commits

Commits with the following prefixes do **not** trigger a new release unless they explicitly contain a breaking change:

- `docs:` Documentation improvements
- `chore:` Toolchain, dependency, or internal CI maintenance
- `test:` Unit, widget, or integration test updates
- `ci:` Workflow and automation changes
- `refactor:` Code refactoring without behavioral alterations
- `style:` Code style and formatting changes

## 3. Mandatory Build Number Rules

Every release artifact generated by the pipeline enforces strict build number monotonicity:

1. **Strictly Monotonic Increase:** Every new release **must** have a build number strictly greater than the preceding build:
   $$\text{Build}_{\text{new}} > \text{Build}_{\text{previous}}$$
2. **Never Decrement:** Decrementing build numbers is strictly rejected by the automated release tool.
3. **Never Reuse:** Build numbers cannot be reused, ensuring compatibility with Google Play and Apple App Store distribution systems.

Example progression:
```text
1.0.0+1  (Initial Release)
1.0.1+2  (Patch)
1.1.0+3  (Minor)
1.1.1+4  (Patch)
2.0.0+5  (Major)
```

## 4. Automation Workflow

The release lifecycle proceeds in the following deterministic sequence:

```text
Merge to main
      ↓
Calculate next SemVer & monotonic build number
      ↓
Update pubspec.yaml
      ↓
Commit version: chore(release): vX.Y.Z [skip ci]
      ↓
Create annotated tag: vX.Y.Z
      ↓
Checkout exact tag
      ↓
Run complete test suite & compliance audit
      ↓
Build Android APK & AAB
      ↓
Verify APK identity, badging, and permissions
      ↓
Build iOS release (when signing configured)
      ↓
Generate SHA-256 checksums
      ↓
Publish GitHub Release with release assets
```
